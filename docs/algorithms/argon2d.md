# Argon2 family (argon2d / argon2id)

**Coins:** Credits (CRDS), Dynamic (DYN), Unitus (UIS), Bitweb (WEB), and others
**Algorithm names:** `argon2d250`, `argon2d500`, `argon2d1000`, `argon2d4096`, `argon2d16000`, `argon2id1024`
**Family:** memory-hard proof-of-work (Argon2 KDF)

```
./cpuminer -a argon2d500   -o stratum+tcp://<pool>:<port> -u <wallet> -p x
./cpuminer -a argon2id1024 -o stratum+tcp://<pool>:<port> -u <wallet> -p x   # Bitweb
```

---

## Overview

Argon2 is the winner of the Password Hashing Competition. **Argon2d** is its
data-dependent variant, where memory-access addresses depend on the data being
hashed. That dependency maximises resistance to time–memory tradeoffs (and to GPUs
and ASICs), at the cost of side-channel leakage — irrelevant for proof-of-work.

As a PoW it is straightforward: fill a buffer of `m_cost` KiB of memory, mix it for
`t_cost` passes across `lanes` parallel lanes, and emit a 32-byte tag compared
against the target. There is no chaining of other hashes and no protocol
customization — it uses the standard Bitcoin-style Stratum flow (80-byte header,
32-bit nonce at header word 19).

For every nonce the miner runs Argon2 with both the **password and salt set to the
80-byte block header** (`pwd = salt = header`), producing the 32-byte hash.

## Argon2id vs Argon2d

Most variants here are Argon2**d**. `argon2id1024` (Bitweb) is Argon2**id**, the
hybrid: it uses data-**independent** addressing (like Argon2i) for **pass 0, slices
0 and 1**, and data-**dependent** addressing (like Argon2d) for everything after
that. In the data-independent regime the reference-block indices come from a
keystream generated by running the compression function over a counter block
(`next_addresses()` in `opt.c`) rather than from the previous block's contents.

Two consequences worth knowing:

- The Argon2 **type is folded into H0**, alongside the cost parameters. So Argon2id
  and Argon2d produce completely different digests for the same header and same
  `t`/`m`/`p` — the type is as consensus-critical as the version.
- The data-independent path needs two 1 KiB **stack-local** blocks. They are handed
  to `fill_block`, which uses alignment-requiring `_mm512_load_si512` /
  `_mm256_load_si256`, so `block` carries `__attribute__((aligned(64)))`
  (`core.h`). Without it Argon2id segfaults on AVX2 and AVX-512 while SSE2 passes.

## Variants

The variants differ only in Argon2 type and cost parameters — and the type and
version are both consensus-critical:

| Algo | type | memory `m_cost` | passes `t_cost` | lanes | Argon2 version | Coin |
|---|---|---|---|---|---|---|
| `argon2d250`   | Argon2d  | 250 KiB   | 1 | 4 | 1.0 | Credits (CRDS) |
| `argon2d500`   | Argon2d  | 500 KiB   | 2 | 8 | 1.0 | Dynamic (DYN) |
| `argon2d1000`  | Argon2d  | 1000 KiB  | 2 | 8 | 1.0 | — |
| `argon2d4096`  | Argon2d  | 4096 KiB (4 MiB) | 1 | 1 | **1.3** | Unitus (UIS) |
| `argon2d16000` | Argon2d  | 16000 KiB (~16 MiB) | 1 | 1 | 1.0 | — |
| `argon2id1024` | **Argon2id** | 1024 KiB (1 MiB) | **3** | 1 | **1.3** | Bitweb (WEB) |

Notes:
- **`argon2d4096` and `argon2id1024` use Argon2 version 1.3** (`0x13`); the others
  use version 1.0 (`0x10`). The version changes the indexing/mixing, so it must
  match the coin — this is the easiest detail to get wrong.
- Higher `m_cost` means more RAM per hash. The high-memory variants (`argon2d4096`,
  `argon2d16000`) effectively cap how many threads fit in a machine's RAM.
  `argon2id1024`'s 1 MiB working set fits in L2/L3 on most CPUs, but its `t_cost=3`
  means 3072 `fill_block` calls per hash — 0.75× the compute of `argon2d4096`.
- `argon2id1024` accepts the alias `-a bitweb`.
- All variants output 32 bytes and use a target factor of 65536.

## Performance

- The Argon2 compression function (`fill_block`, built on the BLAKE2b round function)
  has SIMD implementations; the memory fill is the dominant cost.
- Throughput is bound by memory bandwidth and capacity, especially for the larger
  variants — this is the algorithm's intended property, not an inefficiency.

## Verification

Each implementation matches the reference Argon2 output for its parameter set;
correctness is confirmed by pool-accepted shares.

`argon2id1024` additionally carries a startup self-test (`argon2d-kat.h`) pinned to
Bitweb mainnet block **76523**, which the miner refuses to start without. Note that
Bitweb's *block* hash is `sha256d(header)`, Litecoin-style — **not** the Argon2id PoW
hash — so a PoW vector cannot be read off a block explorer's `hash` field; it has to
be recomputed from the raw 80-byte header. The self-test asserts both, so a mistyped
header vector reports itself as such rather than as an Argon2 failure.

## Possible optimizations (preview)

- **Wider `fill_block`** — AVX-512 implementations of the Argon2 compression function
  for CPUs that support it.
- **Allocation reuse** — keep each thread's `m_cost` memory region allocated across
  nonces (and across jobs) instead of allocating per hash, to avoid page-fault and
  zeroing overhead on every attempt.
- **NUMA-aware placement** — pin each thread's memory region to its local NUMA node on
  multi-socket machines so the bandwidth-bound fill stays local.
